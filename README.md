## v3.13 텔레그램 알림
- LONG 또는 SHORT 신호가 **OFF → ON으로 전환되는 순간**에만 텔레그램 메시지를 보냅니다 (30초마다 계속 ON이어도 스팸 발송하지 않음).
- 메시지에는 판정된 방향(LONG/SHORT), 현재가(Binance 실시간가), 진입 1~5 가격과 TP/SL, 감지된 배경색, KST 시각이 포함됩니다.
- 배포 직후(재시작 직후) 첫 수집 사이클에서는 알림을 보내지 않습니다 — 재시작 전부터 이미 ON이었던 상태를 "새로 발생"으로 잘못 알리는 것을 막기 위함입니다. DB에 저장된 마지막 관측치를 기준으로 이전 상태를 복원합니다.
- 필요한 환경변수:
  - `TELEGRAM_BOT_TOKEN` — BotFather에서 발급받은 봇 토큰
  - `TELEGRAM_CHAT_ID` — 메시지를 받을 채팅방/사용자 ID
  - (선택) `TELEGRAM_NOTIFY_OFF=false` — 기본값은 `true`라서 ON→OFF로 꺼질 때도 1회 알림이 갑니다. ON 될 때만 받고 싶으면 `false`로 설정하세요.
  - (선택) `DASHBOARD_URL` — 메시지 마지막 줄에 대시보드 링크를 붙이고 싶으면 설정
- `POST /api/telegram-test` — 신호 발생을 기다리지 않고 텔레그램 설정이 정상인지 바로 확인할 수 있는 테스트 발송 엔드포인트
- `/api/status`의 `telegram` 필드에서 활성화 여부, 마지막 발송 시각/오류, 누적 발송 수를 확인할 수 있습니다.

## v3.18 ON/OFF 둘 다 근거 포함
- 이전에는 OFF(해제) 메시지에 근거 섹션이 통째로 빠졌습니다 — OFF는 정의상 "활성 배경색이 없는 상태"라서, ON 근거를 만드는 로직(`_sig_evidence_text`)이 빈 문자열을 반환했기 때문입니다.
- 이제 ON과 OFF 각각 다른 형태의 "E-RANG 실제 판정 근거"를 보여줍니다:
  - **ON**: 지금 감지된 배경색 + 매치된 CSS 규칙 + 라벨 텍스트
  - **OFF**: 직전에 감지됐던 배경색이 무엇이었는지 + 기본색으로 복귀했다는 사실 + **몇 초/몇 분간 켜져 있다가 꺼졌는지(활성 유지 시간)**
- Binance 지표 참고 섹션도 ON/OFF 각각 "진입 시점" / "해제 시점" 라벨을 붙여서 두 메시지 모두에 포함됩니다.

## v3.70 매일 자동으로 데이터 쌓아주는 GitHub Actions 추가

매일 새로 쌓인 데이터만 자동으로 GitHub 저장소에 커밋해서 누적시킬 수 있게 됐습니다.

- **읽기전용 자동화 토큰 신설**: 로그인 비밀번호와 별개로, `/export.csv`·`/export-signals.csv` 전용 토큰을 만들었습니다. `/settings` 페이지 "📦 자동 데이터 백업" 섹션에서 확인/재발급 가능합니다.
- **증분(incremental) export 지원**: `/export.csv?since_id=마지막ID` 형태로 호출하면 그 이후에 쌓인 행만 반환 — 매일 전체를 다시 받지 않고 새 데이터만 가져와서, 저장소 용량이 불필요하게 계속 배로 커지지 않습니다.
- **GitHub Actions 워크플로우 신설** (`.github/workflows/daily-csv-export.yml`): 매일 KST 자정에 자동 실행, 마지막으로 받은 id를 기억해뒀다가 그 이후 데이터만 받아서 `data/coin_observations.csv`에 이어붙이고 커밋. 수동 실행(workflow_dispatch)도 가능.

**설정 방법**:
1. 앱의 `/settings` 페이지에서 자동화 토큰 복사
2. GitHub 저장소 → Settings → Secrets and variables → Actions → New repository secret
   - `COIN_MONITOR_URL`: 배포된 주소 (예: `https://coin-monitor-production.up.railway.app`)
   - `EXPORT_API_TOKEN`: 위에서 복사한 토큰
3. 그러면 매일 자정 자동으로 `data/coin_observations.csv`가 쌓입니다 (Actions 탭에서 수동 실행도 가능)

토큰 없이 접근/틀린 토큰 접근이 정확히 401로 거부되는지, 올바른 토큰으로는 세션 로그인 없이도 되는지, 재발급하면 예전 토큰이 무효화되는지, 증분(since_id) 필터가 정확히 새 행만 반환하는지까지 전부 테스트로 검증했습니다. 테스트 9개 추가, 전체 245개 통과.

## v3.54 자동매매 진입 트리거 수정 — "신호 켜짐"이 아니라 "진입가에 다가갈 때" ⚠️

**중요한 로직 수정입니다.** 지금까지 자동매매는 E-RANG 신호가 OFF→ON으로 바뀌는 순간 바로 지정가 주문을 넣었는데, 실제 의도는 **"신호가 켜져있는 상태에서 가격이 1차(25%) 진입가 근처로 다가올 때"** 진입하는 거였습니다.

- **수정 전**: 신호 ON 전환 즉시 진입가에 지정가 주문 (가격이 진입가에서 한참 멀어도 일단 주문부터 넣음)
- **수정 후**: 신호가 ON인 동안 **가격이 진입가와 `진입 임박 알림 기준`(기본 $100) 이내로 가까워졌을 때만** 진입 — 텔레그램 "진입 임박" 알림과 완전히 동일한 조건/방식을 그대로 재사용했습니다.
  - 신호는 ON인데 가격이 멀면: 대기만 하고 진입 안 함
  - 그 상태에서 가격이 근처로 오면: 그때 진입 (1회만, 계속 근처에 머물러도 재진입 안 함)
  - 신호가 OFF로 바뀌면: 대기 상태 초기화 (나중에 다시 ON되고 가격이 가까우면 새로 진입 가능)

**검증**: 실제 collect_once() 파이프라인으로 "신호 ON + 가격 2000달러 차이 → 진입 안 함" → "신호 ON 유지 + 가격 50달러 차이로 근접 → 정확히 그 순간 진입" 시나리오를 그대로 재현해서 확인했습니다. 관련 테스트도 전부 새 트리거 방식에 맞게 다시 작성했습니다 (테스트 129개 전부 통과).

## v3.43 포지션 손익 퍼센트에 레버리지가 반영 안 되던 버그 수정
- **버그**: 미실현손익 옆 퍼센트를 `unrealisedPnl ÷ positionBalance × 100`으로 계산했는데, 거래소가 내려주는 `positionBalance` 필드가 실제로는 (마진이 아니라) **포지션 전체 명목가치(notional)와 같은 값**이었던 것으로 보입니다. 그 결과 퍼센트가 레버리지 배수만큼 작게(예: 10배 레버리지인데 실제 수익률의 1/10 수준으로) 나왔습니다.
- **수정**: 이제 `포지션가치(positionValue) ÷ 레버리지(leverage)`로 실제 투입 마진을 직접 계산해서 퍼센트를 냅니다. 두 필드(positionValue, leverage) 다 없을 때만 예전처럼 positionBalance를 그대로 씁니다.
- 검증: 레버리지 10배, positionBalance가 실제로는 명목가치와 같은 상황을 재현해서, 수정 전 0.31% → 수정 후 3.10%(정확히 레버리지가 반영된 값)로 바뀌는 것까지 확인했습니다.

## v3.42 텔레그램 "현재가"가 이상한 값(예: 10.0)으로 나오던 버그 수정
- **버그**: 현재가 추출 정규식이 "현재가"라는 글자 근처에서 가장 가까운 숫자를 무조건 가져오는데, 만약 "현재가 갱신 10.0초 전"처럼 실제 가격과 무관한 작은 숫자(경과 시간, 레버리지 등)가 더 가까이 있으면 그걸 BTC 가격으로 착각했습니다. 그 결과 텔레그램 메시지에 "현재가: 10.0"처럼 실제 진입가(7만~8만대)와 전혀 안 맞는 값이 나갔습니다.
- **수정**: 추출된 후보 숫자가 최소 100 이상일 때만 채택하도록 안전장치를 추가했습니다. 너무 작은 값이 나오면 그 후보는 버리고, 기존에 있던 "본문에서 가장 먼저 나오는 10,000 이상의 숫자" 방식으로 안전하게 대체됩니다.
- 실제 버그 상황("현재가 갱신 10.0초 전" 같은 문구)을 그대로 재현해서 정상적으로 78999.1을 찾는 것까지 확인했습니다.

## v3.38 BingX 자동매매 엔진 추가 (실제 주문 실행 가능 ⚠️)

**E-RANG LONG/SHORT 신호가 ON으로 바뀌는 순간(엣지 트리거), BingX에 자동으로 지정가 주문을 넣는 기능입니다.** 실제 돈이 걸린 기능이라 아래 내용을 꼭 읽어주세요.

### 매매 규칙
- **트리거**: 기존에 이미 만들어져 있던 E-RANG LONG/SHORT ON/OFF 판정 로직을 그대로 재사용합니다. 신호가 OFF→ON으로 바뀌는 순간에만 진입하고, ON 상태가 계속 유지되는 동안에는 추가로 진입하지 않습니다 (텔레그램 알림과 동일한 엣지 트리거 방식).
- **진입가**: E-RANG이 표시하는 **1차(25%) 지정가**로 지정가(LIMIT) 주문을 넣습니다. 가격이 그 값에 도달해야 체결됩니다.
- **TP/SL**: E-RANG이 제공하는 1차 TP/SL 값을 주문에 그대로 첨부합니다 (BingX가 체결 후 자동으로 관리).
- **포지션 크기**: 설정한 고정 USDT 마진 × 레버리지 = 명목가치, 그걸 진입가로 나눠서 수량을 계산합니다 (기본: $50 마진 × 5배).

### 안전장치 (기본값)
- **자동매매 기본 꺼짐(OFF)** — 설정에서 직접 켜야 동작합니다.
- **드라이런(모의) 모드 기본 켜짐(ON)** — 실제 주문 없이 "이 신호면 이렇게 주문 나갔을 것"을 로그로만 남깁니다. 로그를 며칠 확인해서 신뢰가 생기면 그때 꺼서 실거래로 전환하세요.
- **중복 진입 방지**: 진입 직전 BingX에 실제로 해당 방향 포지션이 열려있는지 실시간으로 확인합니다. **이 확인 자체가 실패하면(네트워크 오류 등) "이미 있다고 가정하고 건너뜁니다"** (fail-closed — 애매하면 무조건 안전한 쪽으로).
- **일일 최대 진입 횟수 / 일일 최대 손실 한도**: 초과하면 그날은 더 이상 진입하지 않습니다 (기본: 10회, -100 USDT).
- **모든 판단(진입/스킵/실패 이유)이 `auto_trades` 테이블에 전부 기록**되고, 대시보드 "🤖 자동매매" 카드와 `/api/auto-trade/log`에서 확인할 수 있습니다.
- **🛑 긴급 정지 버튼** (설정 페이지 + 대시보드): 자동매매를 즉시 끄고, BingX에 걸려있는 미체결 주문을 전부 취소합니다. (이미 체결되어 실제로 열린 포지션 자체는 자동으로 청산하지 않습니다 — TP/SL이 계속 관리 중이므로, 잘못 건드리면 오히려 위험할 수 있어 의도적으로 제외했습니다.)

### ⚠️ 검증 관련 중요 안내
- BingX API의 서명 방식(HMAC-SHA256, 정렬된 쿼리스트링)과 엔드포인트는 사용자가 제공한 공식 문서를 그대로 따랐지만, **TP/SL 파라미터의 정확한 JSON 형식은 문서에 상세 스펙이 없어 이 계열 API의 일반적인 관례를 따라 최선으로 구현**했습니다. 실거래로 전환하기 전에:
  1. 드라이런 로그를 충분히 확인하세요.
  2. BingX가 제공하는 **TEST ORDER 엔드포인트**([20]번, `/openApi/swap/v2/trade/order/test`)로 파라미터가 실제로 유효한지 먼저 확인하는 걸 권장합니다 (`bingx_client.test_order()`).
  3. 처음 실거래 전환 시 아주 작은 금액으로 먼저 테스트하세요.
- Hedge Mode(양방향 포지션, LONG/SHORT 동시 보유)가 계정에 활성화되어 있어야 이 주문 방식(`positionSide=LONG/SHORT`)이 정상 동작합니다. BingX 계정 설정에서 확인해주세요.

## v3.27 "현재 포지션 (추정)" 탭 추가
- Bitget V3 통합계좌 API에는 실시간 포지션 조회 엔드포인트가 없어서, **체결 내역(fills)의 open/close를 직접 계산해서 현재 남아있는 포지션을 추정**하는 기능을 추가했습니다 (`bitget_client.compute_open_positions`).
  - 심볼별로 open 체결은 더하고 close 체결은 차감(비례 배분)해서 남은 수량 + 평단가를 계산합니다. 여러 심볼/롱·숏 동시 보유도 각각 독립적으로 추적합니다.
  - 미실현손익은 표시하지 않습니다 — 종목별 실시간 시세가 없어서 억지로 계산하면 틀린 값을 보여줄 위험이 있기 때문입니다. 전체 계좌 미실현 PNL은 계좌자산 API 값을 그대로 씁니다.
  - **한계**: 조회한 체결 내역 범위보다 더 예전에 진입한 포지션이 있으면, 그 이전 open 체결이 안 잡혀서 실제보다 수량이 적게 나올 수 있습니다. 화면에도 이 안내 문구가 항상 보입니다.
- "내 Bitget 계좌" 카드에 **"현재 포지션 (추정)"** 탭을 첫 번째(기본 선택) 탭으로 추가했습니다. 상단 "현재 포지션" 미니 카드도 이 추정 포지션 목록(심볼·LONG/SHORT·수량)을 보여주도록 바꿨습니다.

## v3.26 Bitget Unified Trading Account V3 API로 전면 교체
- v2 mix API(`/api/v2/mix/...`)와 그 추정 변형(`/api/v2/uta/...`)이 모두 실패해서, 사용자가 직접 확인해준 **실제 문서 기반 V3 통합계좌 API**로 완전히 다시 작성했습니다.
- 엔드포인트: `GET /api/v3/account/assets` (계좌 자산), `GET /api/v3/trade/fills?category=USDT-FUTURES` (체결 내역), `GET /api/v3/trade/history-orders?category=USDT-FUTURES` (주문 내역).
- **"오픈 포지션" 개념이 사라졌습니다** — V3 API에 실시간 포지션 목록 엔드포인트가 없어서(문서에 없음), 카드 이름을 "내 Bitget 계좌"로 바꾸고 지표를 재구성했습니다:
  - 요약: 총자산(accountEquity) / USDT 잔고(usdtEquity) / 미실현 PNL(usdtUnrealisedPnl) / 유효자산(effEquity) / 승률 / PNL(통합)
  - 탭: 체결 내역(fills) / 주문 내역(history-orders) — "보유 포지션" 탭은 제거
  - 승률/실현손익은 체결 내역 중 `tradeSide=close`인 것들의 `execPnl`을 집계해서 계산합니다.
  - 상단 미니 카드도 "최근 체결" 기준으로 바뀌었습니다.
- 환경변수: `BITGET_CATEGORY`(기본 `USDT-FUTURES`), `BITGET_SYMBOL`(선택, 특정 심볼만 보고 싶을 때). `BITGET_ACCOUNT_MODULE`은 더 이상 쓰지 않습니다(V3는 mix/uta 구분이 없는 별도 API 트리라서).

## v3.25 통합계좌(UTA) 지원 + 에러 메시지 정확도 개선
- **[40085] Unified Account mode 오류 수정 시도**: 비트겟이 "통합계좌(Unified Trading Account)" 모드인 계정에서 클래식(Classic) 전용 API(`/api/v2/mix/...`)를 호출하면 이 오류가 납니다. 엔드포인트 경로의 계좌 구간(`mix`)을 환경변수 `BITGET_ACCOUNT_MODULE`로 뺐고, 기본값을 `uta`로 바꿨습니다 (클래식 계좌를 쓰는 다른 배포는 `BITGET_ACCOUNT_MODULE=mix`로 되돌리면 됩니다).
  - ⚠️ **주의**: 통합계좌(UTA) API의 정확한 경로/파라미터는 실시간 문서로 검증하지 못한 상태의 최선의 추정입니다 (`/api/v2/uta/...`). 틀렸다면 다른 형태의 오류(404 또는 다른 code/msg)가 나올 텐데, 그 메시지를 알려주시면 경로를 다시 맞출 수 있습니다 — 코드가 아니라 환경변수만 바꾸면 되므로 재배포 없이 바로 테스트 가능합니다.
- **에러 메시지 정확도 개선**: 이전에는 4xx/5xx HTTP 상태에서 `resp.raise_for_status()`가 먼저 터져서 비트겟이 실제로 응답 본문에 담아 보낸 `{code, msg}`(진짜 원인)를 볼 수 없었습니다. 이제 HTTP 상태와 무관하게 먼저 JSON 본문을 파싱해서 비트겟의 실제 에러코드/메시지를 그대로 보여줍니다 (예: `[40085] You are in Unified Account mode...`).

  - **손익비 (TP 거리 ÷ SL 거리)**: 1 미만이면 "낮은 편(SL에 먼저 닿을 위험)", 1~3이면 "무난한 편", 3 초과면 "매우 높은 편(도달 확률 낮을 수 있음)".
  - **15분봉 ATR 대비 TP 거리**: 0.5배 미만이면 "타이트함(빠르게 도달 가능)", 2배 초과면 "먼 편(추세 지속 필요)".
  - **모멘텀 경고**: LONG인데 15분 RSI 70 이상(과매수권), SHORT인데 RSI 30 이하(과매도권)면 되돌림/반등 리스크를 경고. 펀딩비가 한쪽으로 과열(±0.05% 이상)되어 있으면 스퀴즈/커버링 리스크를 경고.
  - LONG/SHORT 진입가 표와 마찬가지로 신호를 촉발한 방향뿐 아니라 **양쪽 다** 항상 표시됩니다.
  - 이 의견은 규칙 기반 자동분석이며, 실제 시장 결과를 보장하지 않는 참고용 정보입니다 (투자 조언 아님).

## v3.19 롱/숏 진입가 동시 표시 + 알림 누락 방지 강화
- 메시지 본문에 트리거된 쪽 한 방향의 진입가만 있던 것을, **LONG/SHORT 진입가·TP·SL을 항상 둘 다** 보여주도록 바꿨습니다 — `[LONG 진입가]` / `[SHORT 진입가]` 두 블록이 매번 같이 옵니다.
- LONG 메시지 작성/전송과 SHORT 메시지 작성/전송을 서로 독립적인 예외 처리로 분리했습니다. 한쪽 메시지를 만들다 예상 못한 오류가 나도 반대쪽 알림은 영향 없이 정상 전송되고, 실패 사유는 로그에 `LONG {ON|OFF} message` / `SHORT {ON|OFF} message` 로 구분되어 남습니다.
- **중요한 구조적 한계**: 신호 감지는 e-rang.kr을 30초(`INTERVAL_SECONDS`)마다 확인하는 방식이라, **두 번의 확인 사이(30초 이내)에 ON→OFF→ON처럼 아주 짧게 깜빡이면 그 사이 상태 변화 자체를 관측할 기회가 없어** 알림이 못 갈 수 있습니다. 이건 코드 버그가 아니라 폴링 주기의 근본적인 한계라서, 이런 짧은 깜빡임까지 다 잡고 싶으면 `INTERVAL_SECONDS`를 더 짧게 낮추는 것 외에는 방법이 없습니다 (다만 너무 짧으면 e-rang.kr 차단 위험이 커집니다).
